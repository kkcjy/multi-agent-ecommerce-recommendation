# 验收问答与PPT四人分工（Q1-Q10专项）

## 1. 目标

本文件用于本次验收准备，覆盖：

1. Q1-Q10 每题的回答准备
2. PPT 制作分工
3. 图纸绘制分工（组件图/部署图/包图）
4. 按要求执行：1 人负责演讲与问答准备，3 人负责画图与做 PPT


## 2. 四人角色分配（固定）

为确保职责清晰，采用以下角色：

1. 成员 A：主讲与问答总负责人
2. 成员 B：架构图与架构类 PPT 负责人
3. 成员 C：部署/虚拟化/安全图与 PPT 负责人
4. 成员 D：UX/性能分析图与 PPT 负责人

## 3. 四人具体任务拆分（本轮验收专项）

## 4.1 成员 A（主讲与问答准备）

职责：1 人专注演讲与问题准备。

任务清单：

1. 完成 Q1-Q10 的口播稿（每题 30-45 秒）
2. 准备追问答案（每题至少 2 个追问）
3. 统一术语与口径，避免四人答辩说法冲突
4. 负责整场时间控制（总时长建议 10-15 分钟）
5. 组织 2 轮彩排并记录问题

交付物：

1. 答辩讲稿
2. 追问题库
3. 彩排问题清单

## 4.2 成员 B（组件图 + 包图 + 架构 PPT）

职责：负责架构相关图纸与页面。

任务清单：

1. 绘制组件图（Q4）

3. 制作架构章节 PPT（系统分层、调用链路、模块职责）
4. 输出一页 MVC 映射辅助图（支持 Q2）

交付物：

1. 组件图 PNG/SVG
2. 包图 PNG/SVG
3. 架构章节 PPT（建议 4-5 页）

## 4.3 成员 C（部署图 + 虚拟化 + 安全 PPT）

3. 制作安全风险与控制措施页（Q8）
4. 准备安全验证案例（未授权、限流、异常输入）

交付物：

1. 部署图 PNG/SVG
2. 虚拟化方案图 PNG/SVG
3. 安全章节 PPT（建议 4-5 页）

## 4.4 成员 D（UX 评估 + 容量规划 + 性能 PPT）

职责：负责体验评估与性能章节。

任务清单：

## 4. Q1-Q10 答题准备模板（每题 10 分）

以下为每题建议回答结构：现状 -> 证据 -> 改进计划 -> 可量化指标。

### Q1 是否设计了纸质原型/线框图/高保真/可操作原型？

建议回答：

1. 已有可操作原型：当前前端页面可直接演示用户与管理端流程
2. 补齐线框与高保真：在 PPT 中展示 User 页面和 Admin 页面的信息结构图
3. 说明迭代轨迹：线框图 -> 高保真视觉稿 -> 当前实现

证据建议：

1. 前端页面截图（用户端、管理端）
2. 线框图导出图（draw.io/Figma）
3. 交互流程图（提交请求、查看结果、记录实验）

### Q2 前端的 MVC 组件（如果有）是什么？

建议回答（按当前项目可落地）：

1. Model：后端 API 数据结构（推荐结果、实验数据、指标数据）
2. View：user.html、admin.html、styles.css
3. Controller：user.js、admin.js（事件处理、请求编排、渲染）

证据建议：

1. 一页 MVC 映射表（文件级）
2. 一张请求时序图（用户点击 -> JS 控制层 -> API -> 返回渲染）

### Q3 你们评估/测试用户体验的计划是什么？

建议回答：

1. 可用性测试：5-8 名同学，完成 3 个任务（推荐、查看实验、提交 outcome）
2. 量化指标：任务完成率、完成时长、错误率、主观满意度
3. 迭代策略：每轮收集问题后优先修复前 3 个高频痛点

证据建议：

1. 测试脚本模板
2. 评分表模板
3. 首轮问题清单与修复前后对比

### Q4 项目的组件图是怎样的？

建议回答：

1. 前端组件：User Portal、Admin Dashboard
2. API 层：FastAPI 路由
3. 编排层：Supervisor / LangGraph
4. Agent 层：UserProfile / ProductRec / MarketingCopy / Inventory
5. 服务层：ABTestEngine / Metrics / FeatureStore
6. 外部依赖：LLM API、Redis、Milvus、DB

证据建议：

1. UML Component Diagram（必须清晰画出依赖箭头）

### Q5 项目的部署图是怎样的？

建议回答：

1. 开发环境：本地 FastAPI + 本地/远端 Redis + LLM 云服务
2. 目标部署：Nginx(可选) + FastAPI(Uvicorn/Gunicorn) + Redis + 向量库 + 监控
3. 数据流：浏览器 -> API -> 编排/Agent -> 存储与外部模型

证据建议：

1. UML Deployment Diagram（节点、容器、网络边界）

### Q6 项目的包图是怎样的？

建议回答（基于当前代码结构）：

1. 包层次：agents、orchestrator、services、models、config、frontend、tests
2. 依赖方向：上层依赖下层，避免反向依赖
3. 当前改进点：减少 Agent 对具体实现的强耦合，使用注入

证据建议：

1. UML Package Diagram（包含依赖方向）

### Q7 是否有使用虚拟化技术的计划？

建议回答：

1. 当前已有 Dockerfile，可容器化部署
2. 计划采用 Docker Compose 管理 API、Redis、监控组件
3. 后续可上云容器平台（如 K8s 或云托管容器）

证据建议：

1. 容器化架构图
2. docker-compose 草案（可在附录展示）

### Q8 项目潜在安全风险与缓解措施？

建议回答：

1. 风险：管理接口未鉴权、CORS 过宽、输入未限长、接口被刷、提示注入风险
2. 缓解：API Key 鉴权、白名单 CORS、输入校验、限流、日志审计
3. 验证：未授权请求被拒、超限请求返回 429、恶意输入被拦截

证据建议：

1. 威胁-防护映射表（Threat -> Control）
2. 安全测试截图或请求示例

### Q9 未来峰值需求/容量是多少？

建议回答（用明确假设）：

1. 初期目标：日活 2k-5k，峰值并发 50-100
2. 中期目标：日活 2w，峰值并发 300-500
3. 核心容量指标：QPS、P95 延迟、错误率、外部 API 调用上限

证据建议：

1. 容量估算表（假设条件要写清）
2. 压测结果截图

### Q10 基于需求/容量的性能瓶颈与改进方案？

建议回答：

1. 潜在瓶颈：LLM 调用延迟、并行 Agent 竞争、内存指标不可扩展、无缓存
2. 改进方案：异步并行优化、短期缓存、降级策略、Prometheus 指标、压测驱动调优
3. 量化目标：P95 < 1200ms，错误率 < 1%，峰值 QPS 提升 2-3 倍

证据建议：

1. 优化前后对比图（延迟/QPS/错误率）
